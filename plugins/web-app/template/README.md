# __APP_TITLE__

TanStack Start and Solid on Cloudflare Workers. Application records are in D1. The auth policy is passkeys, then phone OTP, and sessions are stored in D1. This tree records that policy and the sessions table. It does not run a WebAuthn ceremony or send a phone code. The service worker caches the offline page and uses it only when a navigation fails. The HTML document sends `Cache-Control: private, no-store`. Add `src/pwa/map-cache.ts` only when the app reads the user's location. Poll first. Add a Durable Object only for realtime. This tree does not add payments.

Network calls this app can cause are GitHub, the Cloudflare API when Wrangler deploys, and an HTTPS webhook the user supplies. Credentials stay in a gitignored `.dev.vars`, in `wrangler secret`, or as secrets of the GitHub Environment named below. `.dev.vars.example` names `SESSION_SECRET` and `DEPLOY_WEBHOOK_URL` and has no values. License is MIT, the same terms as the Joules repository `LICENSE`.

`src/server.ts` serves the Solid Start app and one MCP server on the worker's public HTTP path `/mcp`. The only tool is `healthcheck`. It returns `{ "ok": true }` and does not read a secret, a session, or the database. Any external bot can call it. A stdio server is not this endpoint. Handler options stay on https://developers.cloudflare.com/agents/model-context-protocol/apis/handler-api/ . No credential is stored for it.

`.github/workflows/release.yml` runs on every push. A listed branch runs `scripts/release.sh` check, then a deploy job. That job deploys and then notifies. The check job does not receive `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, or `DEPLOY_WEBHOOK_URL`. The deploy step is the only one with `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. The notify step is the only one with `DEPLOY_WEBHOOK_URL`. An unlisted branch prints `skip deploy` and does not start the deploy job. The check job uploads `dist` and `.wrangler/deploy/config.json`. The deploy job downloads both and does not build again. Wrangler follows that redirect to the environment selected at build time. `npm run deploy` calls the same script. The branch is a key in `deploy/branches.json`. The value is the Wrangler environment (`main` is `production`, `staging` is `staging`; add other branches in that file). The same branch names are the ones to connect as Workers Builds triggers. Workers Builds and this workflow must not both deploy one branch. The file is the switch: remove a branch from the file to leave it to Workers Builds, or disconnect Workers Builds for a branch this file deploys.

The deploy job sets `environment: release`. That line does not choose which branches GitHub will release secrets to. A person creates a GitHub Environment named `release`, limits its deployment branches to the branches this file deploys (`main` and `staging` in the template; add a branch there when you add it to the file), and stores `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, and `DEPLOY_WEBHOOK_URL` as secrets of that environment. https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idenvironment

The script builds with `CLOUDFLARE_ENV` set to that environment, then runs `wrangler deploy`. The Vite plugin selects the environment at build time. Deploy commands stay in the `wrangler` skill. Product choice stays in the `cloudflare` skill. https://developers.cloudflare.com/workers/vite-plugin/reference/cloudflare-environments/ https://developers.cloudflare.com/workers/ci-cd/builds/ https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/

The version for a deploy is the `package.json` version plus the short git sha. It is a deploy tag and message, and an `APP_VERSION` var. The workflow does not commit it.

After a successful deploy, `scripts/notify.sh` POSTs JSON to `DEPLOY_WEBHOOK_URL`: app name, branch, environment, version, and deploy result. The URL is never committed and is not written into the log. An empty URL, a non-https URL, or a URL with userinfo fails the step. A redirect is a failure. No connected Cloudflare MCP tool sends that webhook, so the workflow does not pretend one did. Workers Builds can also notify through event subscriptions when Builds is what deploys the branch: https://developers.cloudflare.com/workers/ci-cd/builds/event-subscriptions/

Connecting the Git repository, creating a live D1 database for each environment, creating the GitHub Environment named `release`, and storing `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, and `DEPLOY_WEBHOOK_URL` as secrets of that environment are account steps. The `database_id` values in `wrangler.jsonc` are placeholders. Production and the top-level binding use `__APP_NAME__`. Staging uses `__APP_NAME__-staging`. Each environment needs its own live `database_id`. Bindings are not inherited, so each environment has its own copy. A file in this tree is not a live Cloudflare connection.

`npm test` runs the app tests. `scripts/verify.sh` checks the production build, the PWA files, the Solid server entry, and that the committed tree has no secret-looking strings. It skips `node_modules` and build output. It skips `.env` and `.dev.vars` only when Git ignores them, or when the directory is not a repository. A tracked copy of those files is scanned. It still reads `.dev.vars.example`. `scripts/screenshot.sh` captures `/` and `/offline` from `npm run preview`. The asset server redirects `/offline.html` to `/offline`. The workflow uploads those pictures. `npm run build` is the production build. `npm run cf-typegen` writes `worker-configuration.d.ts` for the D1 binding. That file is generated and gitignored.
